# Bot de atención

Estado (2026-10-07): **etapa local implementada**. Configurar, probar y supervisar el bot por negocio, sin canales conectados. No se envía ningún mensaje real, no hay IA conectada al bot y no hay gasto.

## Qué existe

| Capa                | Archivo                                                           | Responsabilidad                                                                                                                                                                                                                                                                    |
| ------------------- | ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Modelo y validación | `src/lib/bot/model.ts`                                            | Esquema Zod de `bot.json`: comportamiento, horarios bot/equipo, conocimiento, reglas, conversaciones de prueba, actividad. Guía de pasos calculada desde datos guardados.                                                                                                          |
| Motor de simulación | `src/lib/bot/engine.ts`                                           | Determinista, sin proveedor. Reglas obligatorias primero (persona, reclamo, pago, temas restringidos), luego reglas habilitadas por prioridad. Solo conocimiento aprobado y vigente. Sin información → aclaración; segunda vez → derivación. Control humano o pausa → no responde. |
| Operaciones         | `src/lib/bot/operations.ts`                                       | Cada cambio permitido, validado en el servidor y registrado en Actividad (sin textos de mensajes).                                                                                                                                                                                 |
| Persistencia        | `src/lib/bot/store.ts`                                            | `data/businesses/<negocio>/bot.json` (o `data/bot.json` para el negocio histórico), cola de escritura única, escritura atómica, revisión optimista (409). Archivo dañado → error, nunca se sobrescribe.                                                                            |
| API                 | `src/app/api/bot/route.ts`                                        | `GET/POST /api/bot?business=<id>`; sesión Clerk y `requestBusinessId` (cliente solo su organización; ajeno → 404).                                                                                                                                                                 |
| Conexiones          | `src/lib/bot/connections.ts`, `src/features/azra/connections.tsx` | Estados verificables (hoy todo «Sin conectar»), cuatro hechos separados por canal, contrato `ChannelAdapter` sin implementar. | Interfaz            | `src/features/azra/bot/*`                                         | Resumen, Conversaciones, Conocimiento, Comportamiento, Automatizaciones, Probar bot, Actividad y Conexiones. | Respaldo            | `src/app/api/export/route.ts`                                     | El ZIP del negocio incluye `bot.json`.                                                                                                                                                                                                                                             |

Reglas de negocio clave: editar una entrada aprobada la devuelve a borrador; una entrada con fecha de revisión vencida deja de usarse y no puede aprobarse sin actualizarla; una regla nueva o editada queda desactivada hasta una prueba en la que se aplique; sin reglas habilitadas el bot no responde con conocimiento (aclara o deriva); las respuestas de persona se guardan localmente y no se envían.

## Lo que falta para la integración real (no implementado)

1. **Verificar el MCP de GHL** con la cuenta del propietario: herramientas reales, scopes concedidos, si permite leer/enviar mensajes de conversaciones y en qué canales. No se asume que el MCP reciba eventos ni mantenga un bot activo.
2. **Recepción de mensajes**: webhooks de GHL (o API de Conversations) hacia un receptor HTTPS público con verificación de firma. El piloto escucha solo en loopback: hace falta un ejecutor siempre activo (servidor o función) y un túnel/despliegue autorizado.
3. **Envío**: API de GHL con token de ubicación guardado solo en el servidor (nunca en el navegador ni en `NEXT_PUBLIC_*`), idempotencia por id de evento entrante y clave de envío, reintentos con espera creciente, límites por canal (p. ej. ventana de 24 h de WhatsApp, plantillas fuera de ventana).
4. **Estados de conexión** reales por canal: integración GHL, canal disponible, cuenta autorizada y habilitado para el bot, más pendiente/conectado/permisos insuficientes/vencida/error, solo cuando el adaptador pueda comprobarlos.
5. **Motor real**: decidir si la respuesta usa IA (proveedor autorizado y costo dentro de USD 20) o el motor determinista; en ambos casos solo conocimiento aprobado y las mismas reglas obligatorias.
6. **Almacenamiento**: `bot.json` es local y de un solo proceso; con tráfico real hace falta base de datos con aislamiento por negocio, retención y política de datos personales.
